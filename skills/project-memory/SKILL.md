# 项目记忆

把跨会话开发需要保留的长期信息维护在项目根目录的 `PROJECT-MEMORY.md`（及按需拆分的 `docs/memory/` 分册）。

开工前先定位实际项目根目录，检查现有记忆文件、未提交改动以及仓库内的 `AGENTS.md` / `CLAUDE.md` / `.gitattributes`。**项目级明确约定优先于个人全局默认约定**：若仓库对记忆格式、提交拆分或 `merge=union` 只追加策略有现行规定，优先遵守仓库约定；需要切换维护方式时，先经用户确认并在迁移 PR 中同步更新仓库约定。

## 结构：总纲与分册

- **根目录总纲（`PROJECT-MEMORY.md`）**：每次开工必读全文，软预算约 **2,000 token**。包含以下四节（允许留空）：
  - **项目方向**：服务谁，解决什么问题，什么结果才算成功。
  - **项目边界**：跨模块通用的硬约束——哪些结果必须保证，哪些做法禁止，原因与重议条件。
  - **项目偏好**：跨模块有多个合规方案时默认怎么选，为什么，何时可以例外。
  - **关键经验 / 分册索引**：小项目直接记录经验；当模块增多或总纲逼近 2,000 token 时，拆出 `docs/memory/<topic>.md` 分册，本节改为**强触发索引**——写明具体触发动作与必读路径（如「涉及承运商建单、重试或面单 → 必读 `docs/memory/shipping.md`」），不写含糊的大类标题。
- **模块分册（`docs/memory/<topic>.md`）**：按业务域承载两类内容——置顶的**「模块边界与偏好」**（仅约束本模块的红线与默认取舍，避免挤满根文档或被迫伪装成经验）和下方的**「关键经验」**。
- **按需读写**：已精简的总纲每次开工读全文，再按触发索引读取本次涉及的分册；收尾只写本次触及的分册（新增条目追加在对应小节末尾，不重排邻近行）。遇到尚未拆分的超长旧文档时，先看章节标题并用任务关键词（含业务同义词）检索相关条目，不在普通任务中擅自整份改写。

## 权限分界：直接写还是等确认

确认权限跟着条文对未来选择的约束力走，无论写在总纲还是分册、叫什么标题都不改变权限：

- **直接维护（事实与经验）**：仅帮助下次更快定位原因、少走弯路的客观事实与排查依据。可直接新增、纠错或标记失效。
  - 例：「承运商返回未建单实为面单余额不足，排查先核对受理回执号与请求时刻」。
- **必须用户确认（全局及模块的方向、边界、偏好）**：凡是限制未来可选做法、不照做即算违规，或影响用户可见行为、费用、安全与数据风险的长期规则——包括新增、改写、删除、精简压缩，以及把单次经验升级为长期禁令或默认策略。向用户列出「原文 → 拟改原文」、放置位置与理由，获明确确认后才写入。
  - 例：「所有失败订单重试前必须人工审核」「支付重试涉及扣费风险时默认停在待核对」。
  - 用户已在指令中明确指定要写入的规则与适用范围时，该指令即为确认；对本次代码实现的同意、合并 PR 或沉默均不能代替原则确认。

## 经验准入：三不写与两必填

动笔前先问：**下一个开发者在只看代码的情况下，知道这条信息会做出不同选择吗？** 不会就不写。

- **三不写**：
  1. **代码、配置、测试或目录结构里直接能查到的现状不写**：代码本身是唯一事实源，复述实现细节会在下次改代码后变成误导人的过期假情报。
  2. **一次性排查流水账与当前任务进度不写**：详细经过已有 PR、Issue 或模块文档可查时，只留一句结论与出处指针。
  3. **没有写清「为什么」的孤立结论不写**。
- **两必填**：
  1. **原因与失效 / 重议条件**：写明当时依据的事实，以及**什么前提变化时该条作废或需要重新讨论**（如外部页面改版、接口恢复、业务量级变化），避免旧经验永久锁死后续方案。
  2. **显式处理被推翻的旧条**：新事实推翻旧结论时，直接更新原经验条（或在只追加仓库中点名覆盖哪一条），不让两条相反结论无标记并存。

## 日常收尾与专门整理

将「日常顺手记」与「定期大扫除」分开，避免日常分支互相撞车或卡断交付节奏：

- **日常开发收尾**（提 PR、直接合并或交付前检查；评审引入新长期结论时只补查新增部分；纯问答与只读排查不触发）：
  - 无新增直接跳过，沿用项目原有的收尾与归档格式。
  - **局部增量与合并前基线对齐**：日常分支只新增本次条目，或精确更新被本次改动直接推翻的那一条，不顺手重写其他段落。**提 PR 或合入前，先拉取最新目标分支核对本次触及的记忆文件**（仅重读本地工作区看不到已合入主干的其他分支）：两条独立新经验同时保留；改到同一旧条或出现相反结论时，核对事实依据后再合并；若等待期间已确认原则的原文或适用范围在主干发生了变化，按最新原文重新与用户对齐。**不要给分册一律配置 `merge=union`**，以免相反结论或原则改写静默并存。
  - **上线不等确认，立规矩必经确认**：若本次代码实现本身符合现有边界，按项目流程正常完成提交、PR 或部署，不要因等待新增原则的文字确认而卡住已授权交付。同时包含客观事实与原则提议时，先把客观事实与排查经验写入记忆防丢失；再将值得跟进的「方向 / 边界 / 偏好」提案附上本次 PR 号或任务出处，集中列在**收尾汇报正文末尾（若项目有归档判定卡等固定尾行约定，放在该尾行之前）**，待用户确认后再写入总纲或对应分册。仅当**本次实现本身将突破现有边界或改变核心方向**时，才先停下确认再动手。
- **专门整理（大扫除）**：
  - 当总纲超过约 2,000 token、分册明显重复膨胀或用户点名整理时，在**独立整理任务**中集中合并重复事实、清理已固化的旧过程、拆分 `docs/memory/<topic>.md` 分册。
  - 按未来影响与遗漏后果取舍，低频但高风险的关键边界持续保留；涉及总纲前三节或分册「模块边界与偏好」的任何增删改，集中列出变更清单交用户一次确认。

## 建档与存量分步迁移

- **新项目建档**：首次进入尚未建档的项目时，从用户描述、README、已有配置和约定起草四节，只询问会影响关键判断的缺口。将原则草案交用户逐项或整批确认，文件里只写已确认条文；无需一次访谈完所有问题。
- **存量长文分步迁移**（面对上百行旧记忆或只追加长文时，分批梳理且保持全程无规则空窗）：
  1. **原位起草（确认前不动原文件）**：保留他人未提交改动，原 `PROJECT-MEMORY.md` 保持原位不动，确保并行窗口仍能读到现行边界。识别旧文中的现行原则与前后冲突，在会话中起草 2,000 token 以内的「新总纲草案 + 分册与归档索引」交用户确认；冲突或待确认的旧原则单列说明，确认前保留原意。尚未梳理拆册的模块，必须在索引中写明「涉及该模块仍须按关键词查阅归档旧文」的兜底入口。
  2. **确认后单次原子切换**：获用户确认后，在**同一提交 / PR** 中一并完成：将原长文移至归档（如 `docs/memory/archive-YYYY-MM-DD.md`）、写入新 `PROJECT-MEMORY.md`（含未拆模块回查归档入口）、同步切换仓库内 `AGENTS.md` / `CLAUDE.md` / `.gitattributes` 的记忆读写约定，消除新旧规则断档期。
  3. **按需渐进迁入分册**：后续日常开发改到哪个业务模块，再把归档中该模块仍有效的经验（核实后直接迁入）与模块边界（经用户确认后置顶写入）迁入对应 `docs/memory/<topic>.md`，同步更新总纲索引入口。
