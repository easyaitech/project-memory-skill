# 项目记忆

把跨会话开发需要保留的长期信息维护在项目根目录的 `PROJECT-MEMORY.md`（及按需拆分的 `docs/memory/` 分册）。

- **开工检查**：定位实际项目根目录，检查现有记忆文件、未提交改动及仓库指令。**项目级明确约定优先于个人全局默认约定**。
- **单一事实源**：已写在 `AGENTS.md`、`CONTEXT.md`、ADR 等现行文档中的规矩或结构，记忆不重抄全文，只留一句结论与指针；已被测试或代码硬闸覆盖（重犯会自动报错）的经验，把原因留在测试旁并从记忆删除。
- **迁移入口**：仅当用户点名将超长或只追加的旧记忆改为「总纲 + 分册」时，先读 [`references/migration.md`](references/migration.md) 再动手；读之前不移动、不重写现有记忆文件。日常任务遇到未拆分的超长旧文，先看标题并用任务关键词（含业务同义词）检索相关条目，按仓库现行约定追加，最多在汇报里建议一次迁移。

## 结构与体积预算

- **根目录总纲（`PROJECT-MEMORY.md`）**：软预算约 **2,000 字**（`wc -m` 可查），总纲不配 `merge=union`。已精简的总纲每次开工读全文，包含四节（允许留空）：
  - **项目方向**：服务谁，解决什么问题，什么结果算成功。
  - **项目边界**：跨模块通用的硬约束——必须保证什么、禁止什么、原因与重议条件。
  - **项目偏好**：跨模块有多个合规方案时默认怎么选、原因与例外条件。
  - **关键经验 / 分册索引**：小项目直接记经验（含试过并放弃的方案及原因）；模块增多或总纲逼近 2,000 字时，沿用项目模块划分拆出 `docs/memory/<topic>.md` 分册，本节改为**强触发索引**（例：「涉及承运商建单、重试或面单 → 必读 `docs/memory/shipping.md`」）。
- **模块分册（`docs/memory/<topic>.md`）**：单册软预算约 **3,000 字**。置顶放**「模块边界与偏好」**（仅约束本模块的红线与默认取舍），下方放**「关键经验」**。日常按触发索引只读写本次涉及的分册。
- **新项目建档**：首次进入无记忆的项目时，从用户描述、README、配置与约定起草四节，只询问影响关键判断的缺口；原则草案经用户确认后落盘。

## 权限分界：按「谁拍板」与「是否立规矩」划线

无论写在总纲还是分册，确认权限一律跟着条文性质走：

- **直接写入（无需二次确认）**：
  1. **客观事实与排查经验**（含试过并放弃的技术方案及原因）：只陈述「发生了什么、原因与前提、下次先查哪里」。
  2. **用户在本次任务中已明确拍板的取舍或规则**：附「日期 + 用户确认 / PR 出处」直接记入对应边界或偏好，不重复追问；存量迁移时保持原意的原文搬迁也不需重审。
- **必须先提议、等用户确认后再写入**：
  - **AI 自己从单次经历归纳出的长期规则**——凡限制未来可选做法、写出「以后都必须 / 禁止 / 默认…」，或影响用户可见行为、费用、安全与数据风险的条文（含对已有原则的改写、删除与压缩）。对本次代码实现的同意、合并 PR 或沉默均不代替规则确认。

## 经验准入与单条定形

动笔前先问：**下一个开发者只看代码和现行文档，知道这条信息会做出不同选择吗？** 不会就不写。

- **三不写**：代码、配置、测试或目录里直接能查到的现状不写；一次性排查流水账与进度不写；没有原因的孤立结论不写。
- **三句定形**：单条经验控制在**三句以内**——①现象或触发场景、②结论与排查动作、③所依据的前提（前提变了该条即作废），末尾附 PR 号；详细经过留在 PR 描述里。
  - 例：「4PX 报未建单实为面单余额校验阻断，运单已受理（#1352）。排查先核对请求时刻与受理回执号，勿凭取面单失败重建运单。前提：承运商仍将建单受理与取面单分步校验。」

## 日常收尾与专门整理

有改动的会话在提 PR、直接合并或交付前执行以下三步（评审引入新长期结论时只补查新增部分；纯问答与只读排查跳过）：

1. **判有无新增**：按准入问题检查；无新增则跳过，沿用项目原有收尾格式。
2. **按文件合并策略写经验**（用 `git check-attr merge -- <文件>` 核实）：
   - **未配 `merge=union`**：只新增本次条目，或直接改正、删除本次读到且已核实过期的经验；提 PR 或合入前先拉取最新目标分支核对触及的文件（独立经验并存，同条冲突或相反结论核实依据后合并）。
   - **配了 `merge=union`**：经验只在末尾追加；旧条过期或被推翻时在末尾追加「覆盖 YYYY-MM-DD『旧条关键词』：…」，同一主题以最后一条为准，删除与合并留给整理任务。
   - **置顶原则区**：总纲与分册置顶的边界、偏好经确认后均原地修改；在配了 `union` 的文件里改原则或做整理，合入后复查一次，删掉可能被拼回的旧行。
3. **合规交付先行，规则提案留痕**：代码本身符合现有边界时正常提交、提 PR 或部署（仅当本次实现本身将突破现有边界时才先停下确认）。记忆文件内**不写任何未获确认的规则或「待定」标签**；把值得跟进的规则提案写在收尾汇报和 PR 描述的固定小标题**「待确认的规则提案」**下（放在项目固定收尾格式之前），只提一次，用户未回即视为未采纳，同问题再犯时带两次 PR 号重提。写入后若总纲超 2,000 字或单册超 3,000 字，本次不顺手大改，在汇报里提示「建议单开整理任务」。

**专门整理（大扫除）**：在独立整理任务中集中合并重复经验、删除过期或已入测试的条目、拆分超长分册；涉及全局或模块原则增删改时，集中列出「原文 → 拟改原文」清单交用户一次确认。
