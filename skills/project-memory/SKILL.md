# 项目记忆

把下次开发需要知道的长期信息放在项目根目录的 `PROJECT-MEMORY.md`。定位到实际项目根目录，沿用同一份记忆；先检查已有文件和未提交改动。日常开工读精简版，旧长文先看标题，再按任务定位相关段落。

## 建档

首次进入尚未建档的项目开发时，从用户描述、README、已有决策和项目约定中起草，只询问会影响判断的缺口。使用下面四节，允许留空。把前三节的拟议条文放在会话里请用户逐项或整批确认；文件里只写已确认条文。无需一次访谈完所有问题。

- **项目方向**：服务谁，解决什么问题，什么结果才算成功。
- **项目边界**：在什么情况下，哪些结果必须保证，哪些做法禁止。
- **项目偏好**：有多个合规选项时默认怎么选，为什么，何时可以例外。
- **关键经验**：下次遇到什么情况，该依据什么事实作判断。必要时附项目内的证据位置。

迁移已有记忆时，保留可追溯的原文和他人改动。先识别旧规则、现行约定和冲突，再提出精简后的条文。待确认的旧原则保留原状，向用户列出冲突及适用范围。若仓库仍要求只追加，与用户讨论并落实维护规则的迁移。

## 确认权限

按条文的含义判断。凡是新增、改写、删除方向、边界、偏好，包括精简或把事实提升为长期要求，都向用户列出「原文 → 拟改原文」和理由，等明确确认后写入。可逐条同意。用户已经明确指定写入的文字、类别和范围时，这次指示即为确认。对本次实现的同意、合并 PR、沉默均不能代替确认。

有依据的事实、经验和必要过程可直接补充、纠错或精简。只保留下次可能改变选择的内容；详细经过已有出处时给出短结论和指针。例如「本次重试导致订单重复」是事实，「可先核对订单号排查重复」是经验，「所有订单重试前必须人工审核」是边界提案。放在哪一节不改变确认权限。

## 有改动的会话收尾

在提交 PR 前检查；直接合入主干则在合并前检查，无 PR 的任务在交付前检查。评审引入新的长期结论时只复查新增部分。问：下一个开发者知道本次结论，会做出不同选择吗？

- 无新增就跳过，沿用项目已有的收尾反馈格式。纯问答或只读排查无需为此写文档。
- 有事实或经验时直接更新对应条目。有原则性提案时集中发给用户；等待期间可以继续已获授权且符合现有边界的工作。若实施本身将突破现有边界，先确认再动手。
- 落笔前重新核对当前文件、已确认的措辞和并发修改；若原文或适用范围变化后影响确认内容，重新对齐。遵循仓库的提交、评审和归档约定。

## 篇幅

以约 2,000 token 为整份文档的软预算，用作整理提示。优先合并重复事实、移除一次性过程、引用模块文档。按未来影响和遗漏后果取舍，年龄和使用频率只是参考。低频的关键边界持续有效；如果精简需要更改前三节，走同一确认流程。
